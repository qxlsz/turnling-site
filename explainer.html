Attributing Subagent Work in Coding-Agent Protocol Adapters

Rajasekhar Josyula · Lakshmi Sravya Vedantham

Transcript

When a subagent outlives the request that started it, which request gets credit for its work? An editor sends each request to an ACP adapter. The adapter drives Codex and tells the editor which files each request changed. Request A’s turn starts a subagent, c, on a thread of its own. Whatever c does, it does for A. The adapter keeps one report per request: the files that request changed.

The user cancels A. That ends A’s own turn, but not c, which keeps working. The user sends request B. The adapter now treats B as the current request. c’s start message only now reaches the adapter. Messages from different threads can arrive in any order. c edits a.txt. That edit was made for A. The adapter asks only which request is current. The answer is B, so a.txt goes into B’s report. B edits b.txt, which really is B’s work. B’s report reaches the editor. It lists a.txt, which was made for A. The request id is right and the files are wrong, and the editor cannot tell. The paper calls this arrival-time attribution. We found it in both the Codex and the Claude ACP adapters.

Each thread delivers its own messages in order. Nothing orders one thread’s messages against another’s. Here is the order from before: a.txt arrives after B starts, so it lands in B’s report. The same work in another order: a.txt arrives before B starts, and B’s report is right. Here c starts early, but its edit still arrives during B. Wrong again. Here the edit arrives after B ends. Right. Which report a.txt lands in depends only on the order. So Turnstile tries every order its model of the provider allows.

Turnstile runs the real, unmodified adapter against a scripted Codex and feeds it one message at a time. Wherever more than one thread could deliver next, it branches. Each path through this tree is one schedule. Each schedule runs in a fresh adapter process. An oracle checks every report against a hidden ledger of who each edit was made for. No language model is involved. Every failing schedule is re-run three times and counts only if it fails the same way each time. Three Codex scenario groups, with A cancelled, interrupted or completed, give 956 schedules. Each square is one of them, coloured from the final runs. On the original adapter, 581 of the 956 put an edit made for A in B’s report.

Sort them by when c’s edit reaches the adapter: not during B at all, or during B with c started before or after B. The original adapter credits the edit when it arrives, so every edit that arrives during B fails, whenever c started. Start-time binding ties c to the request that is current when c’s start message arrives. If c started before B, that is A, and the edit stays out of B’s report. 407 schedules are fixed. But c’s start message can itself arrive after B starts. Then c is tied to B, and 174 schedules still fail. Dispatch-time binding reads the spawn item instead. Codex sends it under A’s turn, and it names c’s thread. The order no longer matters. In every scenario we ran, no schedule misattributes. The price: work it cannot tie to a dispatch is left out, and the report says it may be incomplete. In sibling and grandchild scenarios that drops B’s own child edit in 226 of 996 schedules. On the Claude adapter, 39 of 111 schedules misattribute, and start-time binding removes all 39.

Could a smarter adapter always get this right? Under the paper’s conditions, on the typed Codex 0.160.1 wire, no. Two runs, E and E′. A spawns c, and A and B each send c some mail. In E, A’s mail is a task and B’s is a plain message. In E′ it is the other way round. c’s turn is stopped, and a new turn u picks up both mails. Its parent is whoever sent the task: A in E, B in E′. So x is A’s work in E and B’s work in E′. None of that reaches the adapter. Both kinds of mail produce the same item, and u’s parent is not on the typed wire. The adapter gets exactly the same messages in both runs, so it must write the same report for B. If B’s report lists x, it is wrong in E. If it leaves x out, it misses B’s own edit in E′. Either way, one run is wrong. That is Theorem 1. The best an adapter can do there is to be safe: leave uncertain work out, and say the report may be incomplete. Origin carried on the event stream is enough. Codex 0.162.0 adds a rootTurnId to each turn, and it tells E from E′. Neither the pinned nor the current codex-acp reads it yet.

Arrival time is the wrong proxy for the request that caused delegated work. Per-request bookkeeping cannot follow work that outlives its request. Bind such work to the request that dispatched it, or better, put the origin on every delegated event.
